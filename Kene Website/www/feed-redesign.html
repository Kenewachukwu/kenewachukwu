Date:
July 2026 · PR #259
Client:
Mixtape
Services:
Product Design, Information Architecture, Design Systems

Project Background

Mixtape’s footage and scene libraries had grown into something closer to a shared drive than a creative tool — folders, filenames, upload dates. Underneath, though, every clip already carried real signal: what problem it showed, whether it had been proven to convert, who could legally use it. The redesign’s core idea, stated directly in the brief: feeds are a decoded story library, not a DAM — cards should carry grammar, eligibility and proof, not just a thumbnail and a filename.

Give the library a number, not just a pile of files
The masthead leads with library yield — 130 videos decoded into 1,079 usable scenes, tracked against a 56–61% target — before a single thumbnail appears. The reframe only works if the system can prove, in one glance, that raw footage is actually being turned into something.
One pivotable view instead of four separate tabs
Categories and Acts used to be separate views competing for the same screen. We collapsed them into a single Browse view you pivot — by Beat, by Act, or by Category — rather than a fourth tab or a permanently split layout. “Proven” content earns a Wins strip inside that same view instead of a destination of its own, since being proven is a property of a scene, not a different kind of scene.
Beat owns the color axis
Color is a scarce resource on a dense grid, so we assigned it deliberately: Beat (Problem, Testimonial, Payoff, and so on) owns the color backbone of every card, while Category drops down to a filter facet instead of competing for the same visual channel. Scan the grid by color and you’re reading story structure, not folder structure.
Footage still processing gets its own lane
Newly uploaded clips don’t have scenes decoded yet, and showing them in the same grid as finished content just reads as broken. A dedicated processing lane keeps in-flight footage visible — so nothing feels lost — without implying it’s ready to use.
A cold, empty library isn’t a dead end
The empty state’s job is to explain why the library is empty — no eligible content yet, not a bug — and prompt the next upload, rather than just render a blank grid and let the user guess.
Every source video becomes its own decoded detail page
This is the surface the rights system plugs into — the License block from the Creator Rights Management case study lives directly on this page. One source video, one place to see everything derived from it: the scenes it yielded, its rights status, and its performance.
Search finds scenes, not files
Search returns scenes, not source videos — you’re looking for “a dog looking guilty” or “someone reading a review out loud,” not a filename you half-remember. Results stay inside the same pivotable grid, filters and all, instead of dropping into a separate search page.
A heatmap shows what’s missing, not just what exists
The coverage heatmap flips library browsing around: instead of “what do we have,” it answers “what haven’t we shot yet.” A grid of beat × category cells is colored by how thin the coverage is, and every cold cell is clickable — it becomes the brief for the next shoot.
Proof rides along with the scene
“Proven” overlays surface real performance scores, not a designer’s guess. Live proven scenes get their own Wins strip inside Browse, so a scene’s track record travels with it instead of living in a separate analytics dashboard nobody opens.
The cold-start view teaches, it doesn’t just apologize
When there’s no coverage at all yet, the empty state explains the grammar — beat × category × subcategory — it’s about to be populated with, rather than a generic “nothing here.” First-time use doubles as onboarding.
A later engineering pass moved the canonical design system from these Figma frames into code (docs/mixtape/design-system/), with a live reference build seeded on real data. The states above are where those decisions were made.
